# P10 — Server deadline, payment verification and QR reissue

The countdown uses the persisted backend `expiresAt` and `serverNow` with monotonic elapsed time. It does not derive a new ten-minute deadline from browser time. Reload and locale changes read the same attempt and expiry; explicit provider expiry and the backend's blank-expiry fallback are exercised separately. The timer is not a live region announcing every second. At zero the QR and download action disappear, and an owner R13 check is requested once for that attempt. Neither the timer nor successful QR creation marks an order paid or unpaid.

R13 queues the backend worker; it does not fan out to provider Inquiry from the browser. R11 reads persisted state at 15-second intervals while visible, with simultaneous reads coalesced and stale requests aborted on scope cleanup. This interval matches the status-journey spacing in the upstream A21 synthetic load workload; it is not a claim about real PaySolution rate limits. Hidden pages pause those reads. Focus, visibility return and pageshow read fresh state and request a check when expiry still needs verification. A failed check hides the old QR and offers checking again, without permitting another payment attempt.

The approved views distinguish creating, checking, active QR, verification unknown, verified expired/open, verified expired/closed, expired/unavailable, review required and paid. The exact closed-expiry message is shown only for the corresponding backend state. A disabled/unconfigured store is not described as a closed preorder. Existing active QR remains available after preorder closes until its own deadline. Verified real paid time before expiry is accepted even when reconciliation happens later. Paid presentation uses saved order/recipient/amounts, a thank-you message and the account email without claiming email delivery, plus a link to the displayed order details. There is no new payment, buyer edit, receipt or refund action.

Reissue requires both an eligible backend state and `canRequestNewQr`. R12 uses the same order and original request key/revision until the result is known. One additional non-PII field identifies the previously observed attempt; reading that old expired attempt cannot acknowledge an uncertain reissue. Legacy two-field metadata is read conservatively. A regression test first reproduced the previous key being discarded after a failed reissue transport, then verifies retry keeps the same key. New successful attempts have a different reference/PNG while preserving order snapshots, recipient and amounts. Closure between rendering the button and the request is enforced by the real backend and leaves one order/one original provider creation.

The initial Chromium run passed 11/12; the sole failure was a test locator matching both order support and Footer email links. It is scoped to the order main region. The separate reissue-key red proof records an actual client defect, not a provider failure. An initial and final bounded visual inspection covers payment states and the paid layout on mobile, tablet and desktop. Only loader icons animate; expired/unknown status icons remain still. Exact final outcomes, current image hashes and preserved failed logs are recorded in the execution ledger.

A further concurrency regression reproduced an older in-flight R11 response restoring the active QR after R13 had already queued checking. Reads after a write now abort any pre-write read and request a fresh R11; ordinary simultaneous read-only return events still coalesce. An aborted read cannot accept stale data or surface an unrelated transport warning. This correction is verified separately before the final three-engine run; its red proof and the earlier 29/29 Chromium run are retained. It changes request sequencing, not the approved visual layout.

All provider results and QR bytes in these tests are explicitly synthetic and processed by real local API/worker routes in owned schemas of the retained single database. No live merchant, real payment, saved-image bank acceptance, physical phone or real Nipamail delivery is claimed. Those checks remain deferred to User Test, with release `not_ready` and live sales disabled.
