# P07 — Authenticated cart review and conflicts

The cart follows P03 references 03/04: the existing shop Header, four readable progress steps, product images and actual Thai names/options, quantity controls, explicit line totals, one white order summary and one orange primary action. Tablet/desktop place summary alongside items. The action bar and footer use its measured height; the last row remains reachable. No stock limits, free shipping rules, fees, coupon or guest cart were added.

R04–R07 are the source of quantities, line prices and totals. A Bundle is one charged line with quantity in sets; its fixed/selectable component list is informational. Shipping is the server's 5,000 minor units once per order. Unavailable lines remain visible with reasons and explicit edit/remove actions, and missing totals are not displayed as zero. Inline option editing uses actual variants and can merge identical line identities through the backend.

Mutations send the displayed expected cart revision. Controls remain disabled while pending; the UI adopts only validated same-event responses. A stale revision loads the current cart and requires another deliberate edit. A lost reply triggers a read, not another relative increment. If that read fails, the confirmed old display remains and writes/checkout stay blocked until a successful explicit read. Typed quantity drafts reset to confirmed data after failure. A focus/pageshow/visibility refresh shows actual changed prices against values previously displayed in this component's memory; those old prices are not used for billing or persisted in browser storage.

The shared resource now has a guarded `accept` method so Header and cart consume one confirmed result without duplicate cart caches. The method captures its resource key and ignores late acceptance after owner, token, event or unmount changes. Unit regression tests exercise token rotation, another owner and logout. Existing abort/ownership tests remain required. User interaction focus is restored to the same quantity/delete control when it remains available, or the cart heading when a row disappears; disabled controls are not used as focus targets.

Before continuing to checkout, the cart reads current store and cart state again. A store that closed while the page was open cannot proceed. Existing orders remain accessible independently. The checkout form itself is P08; P07 does not claim that a recipient, quote or order exists.

Browser fixtures create isolated synthetic catalog/cart data through actual local backend routes. Tests cover login-before-private-cart, empty state, quantity edits/reload/removal, variant merge, Bundle pricing/counts, real CAS conflict, an actual committed mutation with an aborted reply followed by failed/successful verification reads, paused items, changed prices, close-before-checkout and account replacement. Explicit negative HTTP stubs are labelled in tests; real merchandise writes are not mocked as successes. One initial fixture startup timed out during concurrent development tooling; the serial rerun was investigated after confirming no orphan fixture listener or database wait remained.

All counts/digests and final layout captures are recorded in `execution-state.json` at completion. Synthetic images/prices/options are not production seeds. The single physical database is retained, actual merchant/payment and real-device testing remain User Test, and release remains disabled.

The initial 30-case run passed 27 checks. Two merge checks assumed the first cart row was size M, but the fixture's frozen timestamps allow ID ordering; traces showed the selected row already had size L. The test now locates the actual M option. One Chromium development-server automatic redirect remained on the protected cart view even though login requests returned 200; extending the URL wait did not resolve it. Its root cause was not established, so no production auth behavior was patched speculatively. Production-build checks separately verify auth, quantities, merging and lost-result reads (4/4), then all three engines recheck auth, merging, layout and keyboard focus on that build (9/9). The development failure logs are retained. All 30 unique cases have passing executions across these checks; this is not a claim of a single clean 30-case development run.
