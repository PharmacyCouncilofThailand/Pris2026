# P06 — Product details, variants and Bundle choices

The product route is public and uses canonical R03 data. Detail, option and Bundle screens follow P03's approved 01/02/19 references: existing shop Header, Thai title, square product imagery with a preorder overlay, exact selected price, blue choice controls, quantity, and one blue Add bar. Tablet/desktop place image and detail in two columns. The bar height is measured for content and footer clearance; missing production/shipping information does not create a section or assumed date.

No-option products use the actual enabled default and render no empty size/color fields. Color and size values come from actual variants. Changing color retains a size only when that exact pair remains saleable, otherwise it clears the size and requires another deliberate choice. Disabled combinations cannot be selected. No selectable size/color is chosen automatically. Description and size information render as text with preserved newlines; HTML-like admin text cannot execute.

Bundles display fixed components and their actual quantities/options separately from buyer-selectable components. The price is the administrator's set price, visible before completing choices, and component prices are not added. Quantity means sets. Internal UI selection includes fixed components for readiness/display, as described by P06. The actual API accepts only buyer-selectable component rows and derives fixed BOM rows itself. The P04 resumer now projects the validated selection to that canonical wire shape and persists it before POST. Unknown-result retries reuse the identical saved body/key. Restoring the detail view reconstructs display-only fixed rows without changing that saved request.

The first real Bundle Add exposed the internal-versus-wire distinction (422); the correction is a frontend contract adaptation and does not change API schemas or Backoffice. Unit regression checks assert fixed rows are absent from the POST and that retry bodies/keys remain equal. Browser tests cover both configurable and all-fixed sets against the real local API.

Positive safe integer quantities have no business purchase cap. Disabled or closed products remain readable. A fresh availability failure or a real 409 between validation and Add refreshes product/store data, retains customer-selected IDs, and prompts review rather than substituting a SKU. Refresh failure blocks another Add until recovery. Anonymous Add uses the incumbent login and retains quantity/options; no cart mutation occurs before authentication.

Initial browser diagnostics found stale Next development route discovery (404 before application code). Renaming the interrupted generated dev cache restored discovery temporarily; the test web server now uses Webpack, matching the production build, to avoid recurring Turbopack cache behavior on this Windows workspace. Interrupted generated route typings also caused an initial build diagnostic; no customer source, database or migration was removed. Final build and browser results are recorded separately in the execution ledger.

The combined 39-case run passed 38 checks; Chromium's visual loop hit a development-server manifest JSON error while repeatedly navigating to the same product. The 9-case stable-source recheck passed eight (including unknown fixed-Bundle reload in all engines) but reproduced that one visual-loop failure, so source editing/HMR alone was not established as its cause. The visual loop now resizes the already loaded product page instead of issuing redundant same-URL navigations. Chromium then passed; a final capture run also passed and was visually inspected at all five reference widths/states. Final captures show the actual viewport at scroll zero, avoiding misleading fixed-header positions in a long full-page image. Functional reload is independently exercised by the unknown-result and production-build checks rather than removed from coverage.

All fixture products, variants, photos and amounts are synthetic and isolated in owned schemas of the single retained database. No production defaults or approved sale options were invented. Real credentials/payment and physical-device checks remain User Test, and release remains disabled. Full command results/digests and representative captures are recorded in `execution-state.json` when P06 completes.
