# P05 — Approved storefront integration

The shop uses the verified Backoffice-owned `@conference/merchandise-storefront-view` 1.0.0 artifact, including its CSS, cards, banners, pills and Header tools. Its tarball SHA-256 remains `97bfff8927f1295ccd29f9cb75ce8865453e444832c96f92477e16b7e3f27796`. Host changes mount those tools in the existing Header and supply one owner/event/token-scoped cart resource to the Header and page. Other routes do not mount merchandise data requests.

The eight approved refinements are retained: A layout, B's single-row cart/language/menu tools without a duplicate title, D's quantity badge, solid blue active category pills, photo-overlay preorder badges, blue product actions with one orange primary action, measured bottom-bar clearance including the footer, and event branding confined to the existing logo and banner. Grid columns are 2/3/4 at the approved breakpoints. Host styles do not replace shared card/banner styling.

The public catalog reads real local API routes: search debounces 200 ms, category/type/search combine in validated URLs, reset updates atomically, stale responses are ignored, and banner controls support keyboard and touch without autoplay. Unconfigured/draft catalogs expose no invented products/prices or purchase controls. Closed catalogs remain readable. Product-load errors have a retry state rather than being reported as an empty catalog. Badge values use server unit counts, including an accessible full count above 99.

P04's deferred integration is exercised here: anonymous Add first uses the existing login; successful authentication resumes the same non-PII intent once. A lost Add response retains its exact request body/key, including after store closure and rejected-session reauthentication. Reauthentication does not call logout or erase the unknown intent. Explicit logout/account changes still clear foreign intent and owner data. The forced-login flag only applies with a strictly validated shop return URL; ordinary login behavior is preserved.

Browser fixtures use the real backend application and contract validators in guarded, individually owned schemas of the single retained `pris_merchandise_dev_test` database. Synthetic catalog values and fixture JWTs are test data. The incumbent login/SSO response and explicitly named transport failures are mocked; merchandise Add/catalog/cart routes are real. This is not evidence of real provider payment, actual bank-app return or physical-device testing.

Verification details, log digests and counts are recorded in `execution-state.json`. Representative integration captures are `visual/p05-mobile.png` (390×844), `p05-tablet.png` (834×1112), and `p05-desktop.png` (1440×1000). These contain clearly synthetic image assets and are not sale-ready product content. The initial and final capture sets were inspected; no shared-renderer redesign was introduced.

During verification, an initial stale development server was restarted after a prior build, and a WebKit resize failure exposed an inherited logo width transition. Disabling that transition only for shop headers resolved the measured overlap. A red rejected-session test then exposed the missing reauthentication path; it was fixed before task completion. Full rerun results supersede those diagnostic failures without hiding them.

The final 51-case run had 48 passes and three test-harness failures: the framework's route-announcer also has `role=alert`, and waiting for all About-page resources timed out. Scoping the error assertion to the shop and waiting for DOM readiness with a Header assertion corrected these checks without changing product behavior. All nine related checks (both affected tests plus the new reflow test, across three engines) then passed. All 54 unique browser cases have passing executions; the ledger retains the failed run and the resolution instead of claiming a single clean 54-case run. Reflow at 640×450 represents the CSS viewport of a 1280px desktop at 200%; native browser UI zoom remains a User Test check.

Product detail, cart, checkout, QR and order-history application screens remain P06–P11. P03's 25 approved images are references, not implemented purchase screens. Actual credentials, payment, email delivery and physical-device User Test remain deferred; live payment/release stays disabled and the local database is retained.
