# P11 — Account history, immutable details and shipment tracking

The public shop remains readable without authentication. Owner history requires the existing account and uses R10 with event, owner/token and page-scoped resources; invalid query parameters do not trigger a history request. The narrowly allowed `page` query survives login, reload and locale switching without allowing recipient/email/search parameters. A 401 offers the existing forced merchandise reauthentication path with the requested history page intact. Loading, transport failure, an empty first page and a valid page with no results have separate presentations.

R10 summaries show order number, creation time in Thailand, server total and separate payment/delivery badges. The canonical summary contract does not contain item names or recipient snapshots, so those remain in the owner detail rather than adding N+1 private detail reads. Cross-owner and event access is enforced by the real API, and unexpected foreign-event summary data is also rejected by the client. Account replacement does not merge histories or expose the previous account's order/recipient data.

Order details continue to render the original/current backend snapshots, including Bundle components, saved prices, recipient and delivery address. Catalog renames and price changes do not change purchased details. When Admin appends an allowed amendment, current data is labelled and a native disclosure retains the original items/options/amounts and recipient/address. There are no buyer edit, cancellation, refund, guest OTP or legacy registration receipt controls. A paid unshipped order remains visibly awaiting shipment, while a shipped order uses the approved read-only detail layout.

Manual fulfillment data displays the actual carrier, tracking string and Thai shipment time. Leading zeroes are preserved; no carrier URL or carrier API is invented. Copy feedback follows the clipboard result, and a denied write leaves the visible number available for manual selection. Browser tests explicitly replace the clipboard boundary with success/denial adapters and do not read or modify the machine clipboard. Paid order pages also refresh on return so newly recorded shipment information appears without a new payment attempt. The unboxing-video guidance and support address are present without adding a new return/refund policy.

The initial Chromium run passed 13/14. The failed pagination case had already navigated/reloaded correctly, but its test selected the visible letters `EN` instead of the Header's descriptive accessible label. The test now uses that existing label; no Header behavior changed. Initial viewport inspection also found the shared direct-child width rule overriding the history panel's approved 900-pixel Desktop width. A content wrapper preserves the 1160-pixel host alignment while allowing the list width, and the empty page now keeps the Footer below its initial viewport. These are scoped corrections, not a redesign. Initial and confirmation viewport inspections cover seven mobile/tablet/desktop layouts; exact final outcomes and hashes are recorded in the execution ledger.

The local fixture creates orders, payment evidence, shipping and amendments through real backend services/routes in owned schemas of the retained single development database. Prices, carriers, addresses, payment evidence and images are synthetic. Real merchant, bank/physical-device and actual Nipamail delivery tests remain deferred to User Test. Release remains `not_ready`, live sales stay disabled and the database is retained until an explicit deletion instruction.
