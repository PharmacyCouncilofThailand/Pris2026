## Responsive

- Mobile 390px เป็นภาพหลักทุกขั้นตอน; ตรวจ overflow เพิ่มที่ 320/430px
- ฟอร์มบนมือถือเรียงตามลำดับกรอก; ตำบล/อำเภอและจังหวัด/รหัสไปรษณีย์ใช้สองช่องในแถวเมื่อมีพื้นที่ ที่ 320px เปลี่ยนเป็นแถวเดียว
- Tablet 834px แยกเนื้อหาและสรุปยอดสองคอลัมน์; ยังใช้ Header ขนาดกะทัดรัด
- Desktop 1440px ใช้พื้นที่เนื้อหาสูงสุด 1160px; สินค้าเป็นภาพ/รายละเอียดสองคอลัมน์; checkout และ QR มีข้อมูลประกอบด้านข้าง
- หน้าร้านเดิมยังยึด renderer 2/3/4 คอลัมน์ ไม่เปลี่ยนด้วยเอกสารนี้
- ภาพเต็มหน้าแสดง dock ที่ปลายภาพเพื่อไม่ตัดกลางฟอร์ม ส่วน implementation ต้องติดท้าย viewport และมีพื้นที่สำรองตามแผน ไม่แปลว่าเปลี่ยนเป็นปุ่ม inline

## การจัดวางแต่ละขั้นตอน

### สินค้ารายชิ้นและ Bundle — P06

ชื่อสินค้าอยู่ครั้งเดียวเหนือเนื้อหา ภาพมีป้ายพรีออเดอร์ ราคาแสดงตามตัวเลือกที่เลือก ปุ่ม Add น้ำเงิน ตัวเลือก active น้ำเงินทึบ การเลือกสี/ขนาดต้องแสดงเฉพาะคู่ที่ขายจริงจาก API ไม่มี stock หรือจำนวนซื้อสูงสุดที่ตั้งเพิ่มเอง

ภาพ 01 แสดงสินค้ามีสีและขนาด; ภาพ 19 แสดงสินค้าไม่มีตัวเลือก โดยไม่มีช่องไซซ์/สีว่าง ภาพ 02 แยกส่วนประกอบ Bundle ที่กำหนดตายตัวกับส่วนที่ผู้ซื้อเลือกได้ ราคาชุดไม่บวกส่วนประกอบเพิ่ม จำนวนที่ซื้อเป็นจำนวนชุด

ข้อมูลในภาพเป็น fixture สังเคราะห์เท่านั้น: สีตัวอย่าง A/B ขนาดตัวอย่าง A/B และราคาที่แสดง ไม่ใช่ข้อมูลขายของกระเป๋า/แก้วจริง รูปจริงรอ Admin เติม

ไม่แสดงกำหนดผลิต/จัดส่งหรือตารางไซซ์เมื่อข้อมูลยังว่าง เมื่อมีข้อมูลจึงแสดงส่วนรายละเอียดตาม API โดยไม่แทรกนโยบายใหม่

### ตะกร้า — P07

รายการแสดงชื่อ ตัวเลือก ราคาต่อหน่วย จำนวน และปุ่มนำออก สรุปค่าสินค้า ค่าส่ง 50 บาทต่อออเดอร์ ยอดรวม และปุ่มดำเนินการต่อสีส้มหนึ่งปุ่ม

เมื่อมีรายการไม่พร้อมขาย รายการยังอยู่พร้อมเหตุผลและทางเลือกนำออก/เลือกใหม่ ยอดที่ยังคำนวณไม่ได้เป็นข้อความ ไม่แทนด้วยศูนย์ ไม่เปลี่ยนตัวเลือกให้เอง และปิดปุ่มไป checkout

หากราคา/เวอร์ชันเปลี่ยน ต้องแจ้งให้ตรวจรายการและยอดปัจจุบันก่อนเดินหน้าต่อ ไม่ยืนยันราคาที่เพิ่มขึ้นอย่างเงียบ ๆ กรณีตะกร้าว่างใช้ข้อความและลิงก์กลับเลือกสินค้า ไม่แสดงยอดซื้อหลอก

### ผู้รับและการตรวจสอบก่อนยืนยัน — P08

ขั้นตอนก่อนยืนยันมีลำดับ ตะกร้า → ที่อยู่ → ตรวจสอบ → ชำระเงิน ไม่สร้างออเดอร์ระหว่างกรอกที่อยู่

บังคับชื่อ–นามสกุล เบอร์โทร ที่อยู่ตามที่มี ตำบล/แขวง อำเภอ/เขต จังหวัด รหัสไปรษณีย์ ประเทศไทยเท่านั้น ชื่อบริษัทและหมายเหตุจัดส่งไม่บังคับ ชื่อ/เบอร์เริ่มจากบัญชีและแก้ได้ ข้อมูลอื่นกรอกเอง ไม่เก็บสมุดที่อยู่หรือเปลี่ยนบัญชี และไม่เก็บข้อมูลผู้รับใน URL/localStorage/sessionStorage

หน้าตรวจสอบแสดงรายการและส่วนประกอบชุด ข้อมูลผู้รับพร้อมแก้ไข ยอดจาก server quote ค่าส่ง 50 บาท ช่องทาง Thai QR PromptPay และข้อความล็อกข้อมูลหลังยืนยัน ปุ่มสุดท้ายระบุยอดเต็มชัด ไม่มี VAT/ใบเสร็จ/coupon/เงื่อนไขที่ยังไม่ได้ยืนยัน

เมื่อกรอกไม่ครบ แสดงข้อความใต้ช่องพร้อม error summary และ implementation ย้าย focus ไปข้อผิดพลาดแรกโดยไม่ล้างค่าที่กรอก

### ยืนยันคำสั่งซื้อและ QR — P09/P10

การยืนยันผลไม่แน่นอนแสดงหน้าตรวจสอบคำขอเดิม มีปุ่มตรวจสอบอีกครั้งเท่านั้น ไม่เสนอสร้างออเดอร์ใหม่ การรีโหลด/กลับจากธนาคารต้องยังเป็นออเดอร์และ attempt เดิม

หลังสร้างออเดอร์ แสดงเลขคำสั่งซื้อ ยอดรวม และสถานะชำระเงินเป็นข้อมูลหลัก ไม่แสดง timeline ก่อนยืนยันซ้ำเพื่อให้ QR อ่านได้ในมือถือ QR ในภาพเป็นพื้นที่วางภาพจริงจาก backend ไม่ใช่ QR ทดสอบที่สแกนจ่ายได้

| สถานะ               | สิ่งที่แสดง / การกระทำ                                                                             |
| ------------------- | -------------------------------------------------------------------------------------------------- |
| กำลังสร้าง QR       | ตัวบอกกำลังทำงาน ปิดปุ่มซ้ำ ไม่มี QR เก่า/ปุ่มสร้างรายการใหม่                                      |
| QR พร้อม            | ยอดรวม เวลาเหลือและ deadline เวลาไทย ภาพ QR ส่วนตัว ปุ่มบันทึกภาพ และตรวจสอบการชำระ                |
| กำลังตรวจสอบ        | สถานะกำลังทำงาน ปิดปุ่มซ้ำ ยังไม่อ้างว่าจ่ายสำเร็จ                                                 |
| ตรวจสอบไม่ได้       | ข้อความ “ตรวจสอบสถานะไม่สำเร็จ กรุณาลองตรวจสอบอีกครั้ง” และปุ่มตรวจสอบอีกครั้ง ไม่มีปุ่มขอ QR ใหม่ |
| หมดอายุ ร้านยังเปิด | หลังตรวจสถานะเดิมยืนยันว่าไม่สำเร็จ จึงเสนอ “ขอ QR ใหม่” สำหรับออเดอร์เดิม                         |
| หมดอายุ ร้านปิดแล้ว | “หมดเวลาชำระเงิน เนื่องจากปิดรับพรีออเดอร์แล้ว” ไม่มีปุ่มขอ QR ใหม่ ยังคงตรวจผลที่แจ้งมาช้าได้     |
| ชำระเงินสำเร็จ      | ขอบคุณ เลขออเดอร์ รายการ/ผู้รับ/ยอดที่บันทึกไว้ ลิงก์รายละเอียด ไม่มี QR หรือปุ่มชำระซ้ำ           |

เวลาในภาพเป็น fixture ไม่ใช่วันเปิดขายหรือหลักฐาน timezone provider การนับจริงต้องใช้ deadline ที่ backend บันทึก ไม่เริ่มใหม่เมื่อ refresh และไม่ใช้เวลารับ Postback ตัดสินเวลาจ่ายจริง QR ที่ออกก่อนปิดร้านยังใช้ได้ภายในอายุเดิม แม้ catalog ปิดแล้ว UI ต้องไม่ซ่อน QR ที่ยังมีสิทธิ์ชำระ

ข้อความขอบคุณใช้ “ระบบจะส่งรายละเอียด…” ไม่อ้างว่าอีเมลส่งถึงแล้วจากสถานะชำระเงินเพียงอย่างเดียว ไม่มี merchantID, credentials, transaction payload หรือ provider URL บนหน้า

### ประวัติและการจัดส่ง — P11

ประวัติแยก badge การชำระเงินและจัดส่ง ใช้ข้อมูลตามบัญชี/event ปัจจุบัน รายละเอียดเก็บข้อมูลที่ซื้อจริง ไม่เปลี่ยนตามสินค้า/ชุดที่ Admin แก้ภายหลัง

ออเดอร์จัดส่งแล้วแสดงบริษัทขนส่ง Tracking ID พร้อมคัดลอก และวันที่จัดส่ง ไม่สร้างลิงก์บริษัทขนส่งที่ยังไม่ยืนยันรูปแบบ URL ไม่มีการแก้ข้อมูลออเดอร์โดยผู้ซื้อ ไม่เพิ่มระบบยกเลิก/คืนเงิน/เอกสารรับเงิน

ช่องทางติดต่อใช้ `pr@pharmacycouncil.org` พร้อมเลขออเดอร์ตามข้อสรุปเดิม ข้อความวิดีโอแกะพัสดุในอีเมลยังคงตาม spec หลัก ไม่ใช่นโยบายคืนเงินที่สร้างขึ้นใหม่

## การตรวจและข้อจำกัด

ตรวจ source และ browser จริงของ Header/about/registration/login/signup/agenda/profile/receipt/ticket/mobile menu/footer ก่อนทำภาพ: 14 route/viewport combinations และ mobile menu โดยหน้า private ใช้บัญชีและ API สังเคราะห์ใน browser context เท่านั้น ไม่มีการใช้บัญชีจริงหรือส่งคำสั่งซื้อจริง

ทำ visual QA รอบแรกครบทุกภาพ แก้รวมหนึ่งชุด และตรวจภาพรอบยืนยันแล้ว การตรวจ static references ครอบคลุม 25 ภาพ และ overflow เพิ่ม 30 combinations ผลอยู่ `layout-checks.json` ภาพไม่มี prototype หรือปุ่มทำธุรกรรมจริง

การตรวจนี้ไม่แทน functional/keyboard/accessibility suite ของ implementation ใน P06–P12 และไม่แทนเงินจริง/มือถือจริง/LINE/ธนาคาร/Nipamail ใน User Test ปัจจุบันยังไม่เปิดขายและไม่ลบฐานข้อมูลพัฒนา

Header ภาพอ้างอิงเป็น schematic ของตำแหน่งเครื่องมือ รายการเมนูเดิมยังต้องคงครบในการพัฒนา Footer สีดำเดิมยังคงใช้จริง; ข้อความท้ายภาพเป็นคำอธิบาย artifact ไม่ใช่ Footer ใหม่ที่จะติดตั้งในเว็บ

## ผลตรวจรับ
