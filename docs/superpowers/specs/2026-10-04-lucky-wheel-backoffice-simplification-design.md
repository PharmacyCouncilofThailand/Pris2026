# Lucky Wheel Backoffice simplification

Date: 2026-10-04. Scope: the existing PRIS Lucky Wheel in `conference-api`, `conference-backoffice`, and `Pris2026`. This design supersedes only the collection-settings, initial-stock, day-selection, QR-reason, and QR-presentation behavior of the earlier Lucky Wheel designs. Daily Main Session check-in, shared QR credits, spin allocation, and staff reward confirmation remain.

## Decisions and boundaries

The administrator has confirmed these changes:

1. Keep one-time staff confirmation that a physical prize was handed over. Remove configurable collection-point instructions and collection deadline from the wheel editor. A winning attendee sees the prize, their reward QR/proof, claim status, and the fixed bilingual instruction: TH “ไปรับของที่จุดรับรางวัล”; EN “Collect your prize at the prize collection point.” Do not show collection-point details or a deadline in attendee UI. Since no deadline is disclosed, a deadline must no longer prevent ordinary confirmation. Preserve existing spin, claim, redemption, and correction records. A no-prize spin still has no reward QR.
2. When an administrator adds a new physical-prize segment, they enter its nonnegative integer initial quantity in the segment form. The first successful publish creates the segment and credits that quantity in the same transaction, with actor/time/before–after evidence in the audit. A repeat request or a later publish cannot add it again. Existing segments display live remaining stock without an editable initial-quantity field. No-prize segments remain unlimited. The Stock surface offers later **top-ups only**; it does not edit the published wheel configuration or reset current stock. Keep historic negative adjustments readable in audit, but reject new negative stock adjustments through the admin API. Top-ups keep idempotency, actor, quantity, before–after, and time; their existing reason requirement stays unchanged because the user only made QR open/close reasons optional.
3. The Rights & QR surface lists configured Bangkok dates for the selected event. Select the last used configured date for that event within the current browser session; otherwise select today if configured, else the nearest future configured date, else the latest past configured date. If there are no configured dates, leave selection empty and offer date creation. The administrator can always choose another date or create a new one. Changing event never carries over the old event's day. The same daily window continues to control both receiving a QR credit and spinning. Schedule-edit reasons remain required, as previously agreed.
4. Opening or closing a QR accepts an omitted or blank reason, normalized to null. Keep actor, timestamps, status, audit snapshots, and idempotency. Revoking a person's unspent credit still requires a reason. Opening a second QR does not close the first.
5. Remove the large-screen projection UI. Each QR row offers an authenticated **Download PNG** action and displays its target PRIS link for review. The QR contains the existing PRIS claim path and opaque QR identifier. Generate the link from the selected event's `events.website_url`, not from a duplicate Lucky Wheel setting. Validate that the URL is an allowed absolute web origin, has no embedded credentials/query/fragment, and differs from the requesting Backoffice origin when that origin is known. In production require HTTPS; local HTTP is allowed for development. If the value is absent or invalid, fail closed with a clear error and no downloadable QR. The local PRIS event currently has `website_url=http://localhost:3001`, while local Backoffice runs on port 3001 and PRIS on port 3003; this event data must be corrected separately before using a local QR. Do not silently change the event URL because other event links use it. Do not add a manual entry code or in-LINE camera dependency.

## Component and API changes

`conference-backoffice` removes the collection-settings form, adds initial quantity only to new prize cards, reduces the Stock surface to later top-ups, preloads configured dates, makes QR status reason optional, and replaces the projection modal with a download action. Keep the existing Backoffice reward lookup and one-time confirmation surface. The downloadable image name should include event, Bangkok date, and a safe QR label; a second download of the same QR reproduces the same target. Show the target URL as text so the administrator can inspect it before distribution.

`conference-api` accepts and validates initial quantity for newly created prize segments without treating it as a later stock edit. The publish transaction writes the segment, initial remaining quantity, and audit together. Existing segment quantity is never recalculated from configuration. A stale `expectedVersion` fails without any stock mutation; a recognized replay returns the previous publish result. The API adds an authenticated event-day listing for Backoffice date selection. QR open/close reason becomes optional in request validation, service, audit, and database consistency constraints. The QR image/read endpoint remains authenticated and now reads `events.website_url`; its API name may change to reflect download rather than projection. The backend stops requiring collection settings to enable the wheel and stops enforcing a hidden collection deadline during reward confirmation. Existing collection columns and historical values remain intact, but new publishing and attendee responses do not depend on them. The migration only relaxes relevant database checks/trigger logic; it does not drop historical tables or records.

`Pris2026` keeps owner-only reward proof, QR, reward history, and claim status. The reward detail displays the fixed bilingual collection instruction. It omits configured collection instructions, deadline, and deadline-expired states. Ownership and staff-only confirmation continue to come from the server.

## Failure handling and verification

Publishing with a malformed quantity, a quantity on a no-prize segment, or an attempt to change an existing segment's initial quantity fails before any stock update. Concurrent publish requests cannot duplicate initial stock. A top-up cannot create negative stock or duplicate the same idempotency key. A QR with a missing/wrong event website URL is not downloaded and tells the admin to correct the event website URL. Download must not open a projection overlay, activate a closed QR, or change receipt counts. QR opening/closing with no reason still records actor/time and retries safely. Date selection must survive tab revisits for the same event and update when the event changes. A reward remains confirmable once, including historical prizes whose old collection deadline has passed; the attendee sees the fixed instruction and accurate status.

Run focused API schema/service/route/PostgreSQL integration tests for these cases, then Backoffice and PRIS typecheck, lint, and production builds. Verify the five UI flows in the running apps with the local database, including the incorrect event URL error and a valid PRIS URL after the administrator sets it. Do not push or deploy as part of this design.
